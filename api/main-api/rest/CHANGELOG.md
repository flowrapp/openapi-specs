## 0.0.120

Spec only. No Main API implementation in this change. Coordinate with BFF API 0.0.114. Next repository tag: `v1.0.30` (after `v1.0.29`). This change does not create the tag. The published solver contract (`api/scheduling_solver/openapi.json`) is unchanged; it is generated by the solver and is not edited here.

Worker profile: photo, phone and identity document (Sergio S1–S7 and the Frontend Architect, 2026-11-13). There is no initial load of photos. `avatarUrl` and the Clerk user id stay empty until a webhook matches the user. Removing a photo deletes it in Clerk for every business of that user. The identity document of an invitation is deleted as soon as the invitation expires. `PERSONAL_DATA_VIEW` protects the phone and the document only. The document is not added to worked-hours reports in this version.

### Added

- `PERSONAL_DATA_VIEW` in `BusinessPermission`. It is core (no feature, no 403 1155), implies `TEAM_VIEW`, and is not added to existing access roles. The OWNER already holds it through every permission. It lets the caller read another member's phone and identity document. Email stays with `TEAM_VIEW`.
- `updateCurrentUserPhone` (`PUT /api/v1/users/me/phone`). Body `UpdateCurrentUserPhoneRequestDTO` `{phone}` required and nullable. `phone` null clears it. E.164 `^\+[1-9][0-9]{6,14}$`, or 400 1161. The phone is not unique. `200` is `CurrentUserResponseDTO` with `Cache-Control: no-store`. The audit records only whether the phone was cleared.
- `getCurrentUserPersonalData` (`GET /api/v1/businesses/{businessId}/users/me/personal-data`). Active membership only. No contract check and no 403 1104. `200` is `MemberPersonalDataDTO` `{phone, identityDocument}`, both nullable, with `Cache-Control: no-store`. `phone` is the stored value and may not be E.164 until the data normalization runs. Not audited. Does not require `PERSONAL_DATA_VIEW`.
- `getBusinessUserPersonalData` (`GET /api/v1/businesses/{businessId}/users/{userId}/personal-data`). OWNER, `PERSONAL_DATA_VIEW`, or the subject. Otherwise 403 1020 (`user lacks permission PERSONAL_DATA_VIEW in business`). An EMPLOYEE without a contract in force receives 403 1104. A target who is not an active member is 404 1126. A read by someone other than the subject is audited without the number or the phone. `Cache-Control: no-store`.
- `replaceBusinessUserIdentityDocument` and `deleteBusinessUserIdentityDocument` (`PUT` and `DELETE /api/v1/businesses/{businessId}/users/{userId}/identity-document`). OWNER only (403 1020, `user is not the owner of business`). `PUT` body is `IdentityDocumentRequestDTO` (`DNI`, `NIE` or `PASSPORT`). The server normalizes (trim, uppercase, strip spaces, hyphens and dots) and returns the normalized document inside `MemberPersonalDataDTO`. Format or a missing part is 400 1158, before a DNI or NIE check letter 400 1159. A document already used by an active member or a pending invitation of this business is 409 1160. The message never includes the number. `DELETE` is an idempotent 204. A removed member keeps the stored document and is not editable here (404 1126). Removed members do not occupy the unique slot.
- `deleteBusinessUserAvatar` (`DELETE /api/v1/businesses/{businessId}/users/{userId}/avatar`). OWNER only. Calls Clerk to delete the profile image. The effect is global for every business of that user. Idempotent 204 when there is no Clerk id or no photo, and when Clerk responds 404. After the 204, the next read returns `avatarUrl: null`. A Clerk 5xx, timeout or 429 is 502 1162, the stored URL is unchanged, and `Retry-After` is forwarded when Clerk sent it. Main uses `CLERK_SECRET_KEY`. No realtime signal.
- `receiveClerkWebhook` (`POST /api/v1/webhooks/clerk`, `x-internal: true`). The mobile app does not call it. Only Clerk does. No bearer token. Verifies the Svix signature with `CLERK_WEBHOOK_SIGNING_SECRET` over the raw body and `svix-id`, `svix-timestamp`, `svix-signature` (tolerance five minutes). Invalid signature is 401 1163. Unreadable JSON is 400 with no functional code. `user.created`, `user.updated` and `user.deleted` set `avatarUrl` (https only, null when Clerk has no uploaded image). Unknown users and other event types return 204 and are ignored. Out-of-order events are ignored. There is no backfill. `clerk_user_id` is stored and is not returned by any operation. A database failure is 5xx so the sender can retry.
- `avatarUrl` (required, nullable URI) on `CurrentUserResponseDTO`, `BusinessUserResponseDTO`, `BusinessUserMembershipDTO`, `AttendanceWorkerDTO`, `TeamScheduleWorkerDTO`, `ShiftChangePersonDTO`, `BusinessWorkedHoursPersonDTO`, `AutoClockingUserSettingDTO`, `GeofencingUserSettingDTO` and `UserHoursDTO`.
- Optional `identityDocument` on `InvitationRequestDTO`. `InvitationResponseDTO` does not return the document. It adds required nullable `hasIdentityDocument`: `true` or `false` only when the caller is the OWNER of the business, and `null` for everyone else. On accept the document is copied to the membership in the same transaction and then cleared. On decline it is cleared. On revoke the row, and the document, are deleted. It is deleted as soon as the invitation expires. A resend after expiry has no document. A resend before expiry keeps it. If acceptance races with another active membership that already has the same document, acceptance still succeeds and the membership is stored without the document.
- Catalog codes 1158 `INVALID_IDENTITY_DOCUMENT_FORMAT` (400), 1159 `INVALID_IDENTITY_DOCUMENT_CHECK_LETTER` (400), 1160 `IDENTITY_DOCUMENT_ALREADY_IN_USE` (409), 1161 `INVALID_PHONE_NUMBER` (400), 1162 `IDENTITY_PROVIDER_UNAVAILABLE` (502) and 1163 `INVALID_WEBHOOK_SIGNATURE` (401).
- `registerUserFromInvitation` applies the same E.164 rule to `phone` (400 1161). `phone` stays required: registration is when it is collected. `maxLength` is 16. Existing stored phones are not rewritten by this contract. Prefixing them with `+34` (Sergio S5) is a data migration and still needs an explicit order. Until that runs, a stored value that is not E.164 does not match a request, and response phones do not enforce the E.164 pattern.

### Changed

- `getCurrentUser`: `phone` is required and nullable, without an E.164 pattern, and `avatarUrl` is required and nullable. `Cache-Control: no-store`. A stored phone may not be E.164 until the data normalization runs. The E.164 pattern stays on `PUT /api/v1/users/me/phone` and on registration.
- `createBusinessInvitation` documents `TEAM_INVITE`, and OWNER when `identityDocument` is present. New errors 1158, 1159 and 1160.
- Code 1126 is also returned by the personal-data and avatar operations when the target is not an active member. It is no longer BFF-only.
- `removeBusinessUser` keeps the identity document of a removed member.

### Removed

- `getUser` (`POST /api/v1/users`) and `UserRequestDTO` / `UserResponseDTO`, including the legacy global `dni`. The operation was not implemented.

### Unchanged

- Worked-hours PDF and CSV. The identity document is not added to reports in this version (phase 2). When it is added, `REPORTS_EXPORT` is enough; removed members keep their document.
- No realtime topic. Lists refresh on the next read.
- `getAttendanceMonth` has no person object and does not gain `avatarUrl`.

## 0.0.110

Spec only. No Main API implementation in this change. Coordinate with BFF API 0.0.100. Next repository tag: `v1.0.15` (after `v1.0.14`). This change does not create the tag. The published solver contract (`api/scheduling_solver/openapi.json`) is unchanged; it is generated by the solver and is not edited here.

### Added

- Split shift: one shift with an optional `segments` array of 1–2 intervals. `ShiftSegmentDTO` (`startTime`/`endTime`) on recurring templates, schedule exceptions, planning requirements and generation input. `ScheduledShiftSegmentDTO` (`startAt`/`endAt`) on scheduled-shift reads and writes, the team schedule and shift-change snapshots and proposal windows. Envelope `startTime`/`endTime` or `startAt`/`endAt` stays required (first segment start, last segment end). Omit `segments`, or send one segment equal to the envelope, for a normal shift. The catalog `BusinessShift` has no default segments.
- Read-only net time on `ScheduledShiftResponseDTO` and `TeamScheduleShiftDTO`: `durationSeconds` and `netSeconds`, same value as `plannedSeconds`. Net time is the sum of the segment durations minus `breakMinutes`. The unpaid gap is not a break and is not included.
- Clock-in notices identify the segment. `notifyShiftClockIn` accepts an optional body `{ segmentIndex }` (0-based, default 0). `ClockInNoticeDTO` and `ShiftClockInNoticeDTO` return `segmentIndex` and `segmentStartAt`. The window, the already-clocked check and the 10-minute cooldown are per segment. An index past the shift's segments is `400` `1047`.

### Changed

- Segments are ordered, non-overlapping, with a gap of at least one minute, on the same logical day. Only the last segment may cross midnight. Each segment must lie inside the day's opening intervals; the gap is not covered by `breakMinutes`. An envelope that does not match the segments is `400` `1050` or `400` `1053` on templates and `400` `1047` on assignments.
- The gap is reserved. Overlap for the same person uses the envelope (end exclusive, so back-to-back is allowed). A shift placed inside the gap is `400` `1047` on a draft replace and a `SHIFT_OVERLAP` warning on a shift-change proposal. A split shift is exchanged or corrected whole, and the shift-change fingerprint includes `segments`.
- Attendance is per segment. Several worklogs may reference the same `scheduledShiftId`. Late, early and a missed segment are per segment. Shift `NO_SHOW` only when every segment is missed.
